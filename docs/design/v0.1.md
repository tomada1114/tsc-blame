# tsc-blame v0.1 design

This document turns the v0.1 requirements into an implementable design. It is the
reference the v0.1 issues point at: each issue names the section it implements, and a
pull request that departs from a section updates this file in the same change.

Status: accepted on 2026-09-01. Every external observation below was re-verified on that
date; the ones marked _(volatile)_ should be checked again before the release.

## 1. Vocabulary and the meaning of "blame"

- **Global metrics (L1)** — the totals `tsc --extendedDiagnostics` prints for a project.
  They are exact, and they are what `--budget` gates on.
- **Symbol table (L2)** — the per-symbol _type footprint_ read from the
  `--generateTrace` type dump. It explains where types are being created; it is not a
  breakdown of L1 and never sums to it.
- **Blame** means _where the cost is charged_: the declaring symbol of a type. The type
  dump carries no usable call-site information, so the tool cannot say which line of
  code caused an instantiation, only which declaration the instantiated type belongs to.
  The README and the CLI output both state this definition before any table.
- **First-party** — a file under the project root that is not under a `node_modules`
  segment and is not a TypeScript `lib.*.d.ts`. Everything else is **external**.
- **Snapshot** — one complete measurement: fingerprint, L1, L2, per project. It is what
  `tsc-blame.json` stores.

## 2. Facts the design rests on

Verified on 2026-09-01 against the npm registry, the `microsoft/TypeScript` repository,
and by running each compiler on a fixture.

1. `typescript@7.0.2` is the Go compiler, published under the plain `typescript` name
   with a `tsc` bin (a Node wrapper that execs a platform-native binary from
   `@typescript/typescript-<platform>-<arch>`). `@typescript/native-preview` stopped
   updating once 7.0 shipped. There is no separate `tsgo` package to support.
2. TypeScript 7.0 ships no programmatic compiler API; 7.1 is expected to ship a new one
   _(volatile)_. `tsc-blame` therefore never imports `typescript`; it only spawns its
   `tsc` bin and reads files.
3. TypeScript 6.0 is the last JavaScript-based release (no 6.1 exists). `6.0.3` still
   accepts `--extendedDiagnostics` and `--generateTrace`. The JavaScript compiler has no
   `--checkers` flag; passing it fails with `TS5025`.
4. The per-type entry schema of the type dump is identical in 5.9.3, 6.0.3 and 7.0.2
   (the same 23 possible keys; only `id`, `recursionId` and `flags` are always present).
   What differs is the file layout: 5.x/6.x write a single `types.json`; 7.x writes
   `legend.json` plus one `types_<checkerId>.json` per checker.
5. In 7.x, `id` restarts at 1 in every shard. An id is only unique as `(checkerId, id)`.
6. `--checkers 1` makes the 7.x dump byte-identical across runs. With the default of 4
   checkers the L1 totals move (e.g. `Types` 28,346 vs 31,919 on the same fixture) and
   the shard contents differ run to run even when the counts look stable.
7. `tsc -b --generateTrace <dir>` writes nothing at all with the Go compiler — the
   directory is not even created. The JavaScript compiler writes `types.<pid>-<n>.json`
   files whose names include the process id.
8. `tsc -p <project> --noEmit --tsBuildInfoFile <tmp> --extendedDiagnostics --generateTrace <tmp>`
   works for a `composite` project in both 5.9.3 and 7.0.2, and produces a dump.
9. `firstDeclaration.path` is absolute. On a case-insensitive file system the compiler
   emits it in lower case while `legend.json` keeps the original case.
10. The Go compiler does not auto-include `@types/*` packages the way the JavaScript
    compiler does; a project that relies on that needs an explicit `types` entry. This
    is the user's configuration, not something the tool compensates for.
11. `--extendedDiagnostics` vocabularies differ: the JavaScript compiler prints
    `Lines of Library` / `Lines of TypeScript` / cache sizes, the Go compiler prints
    `Lines` / `Memory allocs`. Both print `Files`, `Identifiers`, `Symbols`, `Types`,
    `Instantiations` and `Memory used`.
12. The npm name `tsc-blame` is unclaimed _(volatile)_.

## 3. Pipeline and module layout

Four stages, each with a boundary type declared in `src/snapshot.ts`:

```
measure  ─▶  Measurement[]      one per project: L1 totals + a trace directory
parse    ─▶  AsyncIterable<TypeEntry>   streamed from the dump, layout-adapted
attribute ─▶ Snapshot           first-party symbol table + external/other rows
compare  ─▶  Comparison         fingerprint verdict, deltas, budget verdict
```

Public modules stay flat under `src/`, as the template requires; everything else is
private under `src/internal/`.

```
src/index.ts                     the published contract (§10)
src/cli.ts                       the command (§9); not an import surface
src/errors.ts                    TscBlameError and the ERR_* vocabulary (§11)
src/snapshot.ts                  boundary types, parseSnapshot, serializeSnapshot (§7)
src/measure.ts                   stage 1 facade (§4)
src/analyze.ts                   stages 2+3 facade: Measurement[] -> Snapshot (§5, §6)
src/compare.ts                   stage 4 facade (§8)
src/internal/measure/compiler.ts     resolve the project's typescript, detect the engine
src/internal/measure/projects.ts     tsconfig discovery: references, extends, JSONC
src/internal/measure/run.ts          spawn tsc with the forced flags
src/internal/measure/diagnostics.ts  parse --extendedDiagnostics into L1
src/internal/parse/json-array-stream.ts  streaming JSON array reader
src/internal/parse/layout.ts         single-file vs legend+shards adapter
src/internal/parse/entry.ts          narrow unknown -> TypeEntry
src/internal/attribute/origin.ts     first-party / external / lib / unlocated
src/internal/attribute/symbols.ts    grouping and the symbol key
src/internal/format/text.ts          human-readable report
src/internal/format/json.ts          --json report
```

## 4. Stage 1 — measurement

### 4.1 Compiler resolution

- `typescript` is a peer dependency, range `>=5.0.0 <8`, and is resolved from the
  **project being measured**, not from `tsc-blame`'s own installation: `createRequire`
  rooted at the project directory resolves `typescript/package.json`, and the bin is
  `<that directory>/bin/tsc` for every supported major.
- `--typescript-dir <dir>` (API: `typescriptDir`) overrides the resolution. It exists
  for fixtures and the CI matrix, and is documented as such.
- Resolution happens lazily, after argument parsing, so `--help` and `--version` work
  without the peer installed (the package smoke test runs `--help` in a consumer that
  has no peer).
- The engine is derived from the resolved version's major: `5` and `6` are `js`, `7` is
  `go`. A major outside the peer range prints a warning and continues; the fingerprint
  records the exact version regardless.

### 4.2 Project discovery

- Input is one tsconfig path (`--project`, default `./tsconfig.json`).
- If that config has `references`, the tool walks them transitively, reading each config
  as JSONC (comments and trailing commas stripped by a small hand-written reader) and
  following `extends` (string or array; relative paths, or bare specifiers resolved with
  `createRequire` from the config's directory). The result is a topologically ordered
  list of projects. A root config with `files: []` and only references is measured
  through its references alone.
- Every config file read along the way, including `extends` targets, contributes to the
  fingerprint hash (§8.1).
- `tsc -b` is never used (fact 7). Referenced projects are measured one at a time with
  `-p`, which relies on the referenced outputs already existing. If the compiler reports
  `TS6305` (output not built), the tool fails with `ERR_MEASURE_REFERENCE_NOT_BUILT` and
  tells the user to run their build first.

### 4.3 The measurement command

For each project, in topological order:

```
node <typescript>/bin/tsc -p <config> --noEmit --tsBuildInfoFile <tmp>/<i>.tsbuildinfo
     --extendedDiagnostics --generateTrace <tmp>/<i>   [--checkers 1 when engine = go]
```

- `--checkers 1` is forced for the Go engine and is not user-configurable (fact 6). The
  JavaScript engine is single-threaded and rejects the flag (fact 3); the fingerprint
  records `checkers: 1` for both.
- `--tsBuildInfoFile` points into the temp directory so an existing incremental build
  cannot make the checker skip files. `--noEmit` keeps the run free of side effects.
- The temp directory lives under `os.tmpdir()` and is removed after the snapshot is
  built, unless `--keep-trace <dir>` asks for it to be kept for inspection.
- Type errors do not abort measurement: the dump and the totals are still written. The
  number of reported errors is recorded in L1 as `errors`, and `--init` refuses to write
  a baseline from a run with errors unless `--allow-errors` is given, because a baseline
  taken from a broken build is not comparable to a clean one.
- A non-zero exit that produced no dump, or a signal, is `ERR_MEASURE_COMPILER_FAILED`
  with the compiler's stderr attached.

### 4.4 L1 from `--extendedDiagnostics`

The parser reads stdout line by line with `^(?<key>[A-Za-z ]+):\s+(?<value>\d+)`. L1 is
the deterministic subset both engines print (fact 11):

| Field            | Source line      |
| ---------------- | ---------------- |
| `files`          | `Files`          |
| `identifiers`    | `Identifiers`    |
| `symbols`        | `Symbols`        |
| `types`          | `Types`          |
| `instantiations` | `Instantiations` |

`Memory used` and every timing line are discarded on purpose: they vary by machine, and
a varying number printed next to a deterministic one makes both look approximate. If any
of the five lines is missing, the run fails with `ERR_MEASURE_DIAGNOSTICS_UNPARSED`
rather than reporting zero.

## 5. Stage 2 — parsing the type dump

### 5.1 Layout adapter

`resolveDumpLayout(traceDir)` returns the list of `{ checkerId, typesPath }` to read:

1. If `legend.json` exists, use its entries (`typesPath`, `checkerId`; a legend entry
   without `checkerId` is checker 0). This covers 7.x and any future layout that keeps a
   legend.
2. Otherwise, if `types.json` exists, it is checker 0. This covers 5.x and 6.x.
3. Otherwise `ERR_PARSE_DUMP_MISSING`.

The adapter is the only place that knows about file names. Everything downstream sees
`(checkerId, entry)` pairs.

### 5.2 Streaming reader

Dumps are ~328 bytes per type and reach hundreds of megabytes on large repositories, so
the file is never read whole. `readJsonArray(stream)` is a hand-written scanner over a
`Readable`: it tracks string and escape state and brace depth, slices each depth-1
object out of the chunk buffer, and `JSON.parse`s that object alone. Memory is bounded
by the largest single entry plus one chunk. There is no runtime dependency for this.

### 5.3 Entry narrowing

Each parsed value is narrowed to `TypeEntry`:

```ts
interface TypeEntry {
  id: number;
  checkerId: number;
  flags: readonly string[];
  symbolName?: string;
  firstDeclaration?: { path: string; line: number; character: number };
  display?: string;
  isInstantiation: boolean; // `instantiatedType` present
}
```

An entry without `id` or `flags` fails the run with `ERR_PARSE_ENTRY_SHAPE`; a dump with
zero entries fails with `ERR_PARSE_DUMP_EMPTY`. Unknown extra keys are ignored — a new
key is not a schema break, a missing one is.

## 6. Stage 3 — attribution

### 6.1 Origin classification

`classifyOrigin(path, projectRoot, compilerLibDir)`:

- `lib` — the path is under the resolved compiler's `lib/` directory (for the Go engine
  that is the platform package's `lib/`, fact 1), or its basename matches `lib.*.d.ts`.
- `external` — any `node_modules` path segment.
- `first-party` — under the project root and neither of the above.
- `unlocated` — the entry has no `firstDeclaration`.

Comparison is case-insensitive on both prefix and segments (fact 9), and paths are
normalized to POSIX separators before comparison. The project root is the directory
containing the root tsconfig, and every stored path is POSIX-relative to it.

### 6.2 Symbol key and the anonymous rule

- A **named** symbol is keyed by `file` + `symbolName`. The first line seen for the key
  is stored for display, but the line is not part of the identity, so an unrelated edit
  that shifts lines does not produce a removed-and-added pair in the diff.
- An **anonymous** entry (`symbolName` starting with `__`, e.g. `__type`, `__object`,
  `__function`) is keyed by `file` + `symbolName` + `line:character`, and carries the
  first `display` seen, truncated to 80 characters, as its label. These rows do move
  when lines move; the documentation says so. Folding them into one row was rejected
  because ~18% of first-party entries are anonymous and a growing anonymous object type
  would be invisible; hoisting them to the nearest export needs source parsing and is
  deferred.
- Entries whose `flags` include `TypeParameter` are counted in the project's `other` row
  rather than as symbols: a type parameter named `T` occurs in every file, and keying it
  by file would merge unrelated declarations.

### 6.3 Footprint

For each symbol key: `types` is the number of entries whose `firstDeclaration` resolves
to it; `instantiations` is the subset with `isInstantiation`. An instantiated generic
carries the generic's own declaration as `firstDeclaration`, so no id resolution across
entries is needed and a single streaming pass suffices.

`external`, `lib` and `unlocated` are each one row with the same two counters; `lib` is
folded into `external` in the report and kept separate in the snapshot.

### 6.4 Sanity checks

- Zero entries with a `firstDeclaration` at all → `ERR_ATTRIBUTE_NO_LOCATIONS` (the
  schema changed under us).
- Zero first-party symbols for a project that has at least one source file →
  `ERR_ATTRIBUTE_NO_FIRST_PARTY` (the root or the path normalization is wrong).

Each stage owns its own invariants rather than one central check, so an error names the
stage that noticed it.

## 7. `tsc-blame.json`

Schema version 0; unstable until v1, as the README states. Everything is sorted and
serialized deterministically (`serializeSnapshot`): projects in topological order,
symbols by `file` then `key`, two-space indent, trailing newline, POSIX-relative paths.

```jsonc
{
  "schemaVersion": 0,
  "generatedBy": "tsc-blame 0.1.0",
  "fingerprint": {
    "typescript": "7.0.2",
    "engine": "go",
    "checkers": 1,
    "configHash": "sha256:…",
  },
  "global": {
    "files": 129,
    "identifiers": 0,
    "symbols": 0,
    "types": 0,
    "instantiations": 0,
    "errors": 0,
  },
  "projects": [
    {
      "config": "packages/a/tsconfig.json",
      "global": {
        "files": 65,
        "identifiers": 0,
        "symbols": 0,
        "types": 0,
        "instantiations": 0,
        "errors": 0,
      },
      "symbols": [
        {
          "file": "packages/a/src/schema.ts",
          "name": "DeepPartial",
          "line": 3,
          "types": 120,
          "instantiations": 98,
        },
        {
          "file": "packages/a/src/schema.ts",
          "name": "__type",
          "line": 12,
          "character": 5,
          "display": "{ a: string; b: number }",
          "types": 4,
          "instantiations": 0,
        },
      ],
      "external": { "types": 28000, "instantiations": 27000 },
      "lib": { "types": 3000, "instantiations": 1000 },
      "other": { "types": 40, "instantiations": 0 },
      "unlocated": { "types": 400, "instantiations": 20 },
    },
  ],
  "budget": { "instantiations": { "maxIncrease": "10%" } },
}
```

- `global` at the top is the field-wise sum of the projects' `global`. L1 and L2 use
  distinct names (`global` vs `symbols`) and no output ever prints a sum of `symbols`.
- `budget` is optional and written by `--init` with the default shown.
- `parseSnapshot(unknown)` validates a file read back from disk and rejects any other
  `schemaVersion` with `ERR_SNAPSHOT_UNSUPPORTED`.

## 8. Stage 4 — comparison

### 8.1 Fingerprint

`{ typescript, engine, checkers, configHash }`. `configHash` is the SHA-256 of the
concatenated raw text of every config file discovered in §4.2, each prefixed with its
POSIX-relative path, so a change to any tsconfig — or to the set of projects —
invalidates the baseline. `tsc --showConfig` is not used because its output lists source
files, which would invalidate the baseline on every added file.

Any field mismatch skips the numeric comparison, prints one warning naming the differing
field, and exits 0 (a missed regression beats a false one). Node version, OS and CPU
count are deliberately not part of the fingerprint: the acceptance test for determinism
is precisely that they do not matter.

### 8.2 Diff

`compare(baseline, current)` yields, per project and globally: the L1 delta per field;
symbol rows added, removed, and changed (with absolute and relative deltas, sorted by
`instantiations` delta descending, then `types` delta); and the external/other deltas.
The report marks each first-party row whose `file` is in the `--changed` list.

### 8.3 Budget

The gate reads **L1 `instantiations`** — the exact global figure — never the symbol
table (decision D1). `--budget` compares `current.global.instantiations` against the
baseline and the budget in the baseline file (default `maxIncrease: "10%"`; an absolute
integer is also accepted). Exceeding it exits 1; everything else about the report is
unchanged. Without `--budget` the exit code never depends on the numbers.

## 9. CLI

`node:util`'s `parseArgs` in strict mode; no argument-parsing dependency.

```
tsc-blame [options]

  --project, -p <path>      tsconfig to measure (default ./tsconfig.json)
  --init                    write tsc-blame.json from this run
  --budget                  compare against tsc-blame.json and exit 1 past the budget
  --baseline <path>         baseline file (default ./tsc-blame.json)
  --json                    machine-readable output (schema unstable in v0.x)
  --changed <file>          a file touched by the change under review; repeatable
  --typescript-dir <dir>    use this TypeScript installation instead of the project's
  --keep-trace <dir>        keep the raw trace output here
  --allow-errors            let --init write a baseline from a run with type errors
  --help, -h / --version
```

- Without `--init` or `--budget`, the command measures and prints the report; if a
  baseline exists it also prints the diff, informationally.
- `--changed` is repeatable and holds plain paths. The CLI does not call `git`; the
  GitHub Action computes the list.
- The text report prints, in order: the blame definition (one line), the fingerprint,
  the L1 table, then the L2 table with an explicit heading "not a breakdown of the
  totals above".

Exit codes: `0` success or skipped comparison; `1` budget exceeded; `2` tool error (any
`ERR_*`).

## 10. Public API (`src/index.ts`)

Small on purpose; the CLI and the Action are the product, the API is what lets someone
build another front end.

```ts
export { measure } from "./measure.js"; // (options: MeasureOptions) => Promise<Snapshot>
export { compare } from "./compare.js"; // (baseline, current, options?) => Comparison
export { parseSnapshot, serializeSnapshot } from "./snapshot.js";
export { TscBlameError } from "./errors.js";
export type {
  MeasureOptions,
  Snapshot,
  Fingerprint,
  GlobalMetrics,
  ProjectSnapshot,
  SymbolEntry,
  Comparison,
  SymbolDelta,
  BudgetOptions,
} from "./snapshot.js";
export type { TscBlameErrorCode } from "./errors.js";
```

`measure` is async (it spawns and streams); `compare` is pure. Every symbol carries a
`@public` TSDoc tag and an `@example` that compiles (`tests/docs.test.ts`).

## 11. Errors

One class, `TscBlameError extends Error`, with `code: TscBlameErrorCode`, `stage`, and
an optional `cause`. The codes, by stage:

| Code                               | Meaning                                                 |
| ---------------------------------- | ------------------------------------------------------- |
| `ERR_MEASURE_TYPESCRIPT_MISSING`   | no resolvable `typescript` from the project             |
| `ERR_MEASURE_CONFIG_INVALID`       | tsconfig unreadable, or `extends`/reference dangling    |
| `ERR_MEASURE_REFERENCE_NOT_BUILT`  | `TS6305`: a referenced project has no output            |
| `ERR_MEASURE_COMPILER_FAILED`      | non-zero exit with no dump, or a signal                 |
| `ERR_MEASURE_DIAGNOSTICS_UNPARSED` | an L1 line is missing from `--extendedDiagnostics`      |
| `ERR_PARSE_DUMP_MISSING`           | neither `legend.json` nor `types.json`                  |
| `ERR_PARSE_DUMP_EMPTY`             | a dump with zero entries                                |
| `ERR_PARSE_ENTRY_SHAPE`            | an entry without `id` or `flags`                        |
| `ERR_ATTRIBUTE_NO_LOCATIONS`       | no entry carries `firstDeclaration`                     |
| `ERR_ATTRIBUTE_NO_FIRST_PARTY`     | zero first-party symbols for a project with sources     |
| `ERR_SNAPSHOT_UNSUPPORTED`         | `schemaVersion` this build cannot read                  |
| `ERR_SNAPSHOT_INVALID`             | baseline file is not a snapshot                         |
| `ERR_COMPARE_BASELINE_MISSING`     | `--budget` without a baseline file                      |
| `ERR_INIT_HAS_ERRORS`              | `--init` on a run with type errors, no `--allow-errors` |

The `designing-errors` skill owns the shape; this table owns the vocabulary.

## 12. GitHub Action

A composite action at the repository root (`action.yml`), used as
`tomada1114/tsc-blame@v0`.

- Inputs: `working-directory`, `project`, `budget` (default `false`), `comment` (default
  `true`), `token` (default `github.token`), `version` (npm version to `npx`).
- Steps: compute `--changed` from `git diff --name-only <base>...<head>` for a pull
  request; run `npx tsc-blame@<version> --json [--budget] --changed …`; render the diff
  table as Markdown; create or update one sticky comment (identified by a hidden marker)
  via `gh api`. Requires `pull-requests: write` only when `comment` is on.
- With `budget: false` the step's exit code is forced to 0 after the comment is posted;
  with `budget: true` the CLI's exit code is propagated.
- The action runs on the repository's own pull requests as its integration test, with
  `budget: false`.

## 13. Testing and CI

- **Unit** (no compiler): checked-in, hand-trimmed dumps under `tests/fixtures/dumps/` —
  one 5.x single-file layout and one 7.x legend-plus-shards layout, a few kilobytes each
  — drive the layout adapter, the streaming reader (including chunk boundaries inside
  strings and escapes), narrowing, attribution, serialization, diff and budget. Captured
  `--extendedDiagnostics` stdout for both engines drives the L1 parser. This is where
  the `src/**` coverage floor is met; the spawn itself stays thin.
- **Fixture projects** under `tests/fixtures/projects/`: `basic` (an expensive recursive
  generic, a template-literal type, anonymous object and function types, a `@types` use
  with an explicit `types` entry) and `references` (`packages/a` ← `packages/b` with a
  root config of references only). Neither is linted, formatted or type-checked by the
  repository's own gates.
- **Compilers for fixtures** are installed by `pnpm fixtures:install` into the
  gitignored `tests/fixtures/compilers/<tag>/` with `npm install` — not pnpm — so the
  repository's seven-day release cooldown does not block `next`. The automation tests
  pass `--typescript-dir` pointing there and skip, loudly, when a tag is absent locally.
- **Goldens** are two kinds. An _exact_ golden (the full `tsc-blame.json`) exists only
  for the pinned compiler versions in the fixtures' lockfile and catches regressions in
  the tool's own aggregation. A _structural_ golden — the ordered set of first-party
  symbol keys plus invariants (top row is not `Array`; `external` is present; every
  counter is positive; no symbol sum is printed) — runs against every compiler in the
  matrix, because absolute counts change with every TypeScript minor.
- **Determinism** is asserted in the automation suite by measuring the same fixture
  twice in one test and comparing serialized snapshots byte for byte; the cross-machine
  acceptance criterion is the CI matrix agreeing with a committed fixture baseline.
- **CI**: `ci.yml` gains a `compat` job with matrix `typescript: [5, 7]` (latest of
  each; 6.0.3 is covered by the repository's own devDependency in the existing jobs). A
  separate `ts-next.yml` runs nightly and on demand against `typescript@next` and does
  not block merges: its purpose is to see upstream breakage before users do.

## 14. Decisions and deferrals

Decided on 2026-09-01 by the owner:

- **D1 — Gate on L1 `instantiations`.** Accuracy over table consistency; the output and
  README say the table is not a breakdown.
- **D2 — Anonymous types keep a position-keyed row with `display`.** Not folded, not
  hoisted (§6.2).
- **D3 — Support TypeScript 5.x, 6.x and 7.x.** Peer range `>=5.0.0 <8`. 6.x was omitted
  from the requirements only because it is a bridge release; the dump schema is
  identical and the repository builds itself with 6.0.3.
- **D4 — This document is the design record.** Issues reference it by `path:line`.

Decided in this document, open to revision through a pull request that edits it:

- Monorepos are measured per project with `-p`, never with `-b`, and the snapshot holds
  both per-project and summed L1 (fact 7).
- A run with type errors is measured but cannot become a baseline without
  `--allow-errors` (§4.3).
- Named symbols are keyed without the line; type parameters go to `other` (§6.2).

Deferred beyond v0.1: call-site attribution via the 7.1 API; hoisting anonymous types to
the nearest export; a `budget.metric` switch; JSON schema stabilization; watch mode and
viewers; CI platforms other than GitHub.
